---
title: "RFD-006: Capabilities map generalization"
description: "One open capability map on each manifest; features gate on capabilities, never on version sniffing."
---

**Status: draft · Target: v0.2 · Area: session, versioning**

## Problem

v0.1 defines three ad-hoc capability booleans (`seed`, `snapshot`, `replay`). Each new optional feature (relay, command channels, task, elicitation) needs a declared home, and the [versioning policy](/spec/versioning-policy) doctrine — wire version determines compatibility, capabilities determine optional features — needs a uniform mechanism.

## Proposal

`capabilities` on both manifests becomes an open string→value map with a registry of standard keys (`seed`, `snapshot`, `replay`, `transfer`, `command_channels`, `task`, `elicitation`, `relay`) and `x-<vendor>.` extension keys. Unknown keys are ignored. A feature's normative text states its gating key.

## Compatibility

Shape-compatible with v0.1 (`capabilities` is already an object); purely clarifying plus new standard keys.
